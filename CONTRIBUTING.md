# Contributing

Thanks for your interest in improving this project. Contributions of all sizes
are welcome: bug reports, documentation fixes, event serializers, and tests.

## No CI policy

This project intentionally does **not** use GitHub Actions, GitHub workflows, or
any other form of CI/CD pipeline.

- Never add a `.github/workflows/` directory or any GitHub workflow file to this
  repository.
- Never add CI configuration for this project (e.g. GitHub Actions, CircleCI,
  Travis CI, Jenkins, GitLab CI, Azure Pipelines).
- Do not propose changes that reintroduce automated CI checks.

Changes are built and verified locally by maintainers before merging. If you
think CI is needed, please open an issue to discuss it first — but note that the
project's direction is to remain CI-free.

## Getting started

1. Fork the repository and create a branch from `master`.
2. Install dependencies: `npm ci`.
3. Make your change.
4. Run the checks:

   ```bash
   npm run format
   npm test
   npm run build
   ```

   Or run everything at once with `npm run verify`.

5. Commit the source change **and** the rebuilt `dist/index.js`.

Never edit `dist/index.js` by hand; it is generated by `@vercel/ncc`.

## Project layout

See [docs/development.md](docs/development.md#project-layout) for the module
map. In short:

- `src/` contains the implementation.
- `test/` contains `node:test` suites.
- `docs/` contains user and maintainer documentation.
- `dist/` is the committed bundle used by the action runtime.

## Coding guidelines

- Use CommonJS and Node.js built-ins; keep the action **dependency-free** at
  runtime. Open an issue before proposing a new runtime dependency.
- Prefer small, focused functions with JSDoc for exported behavior.
- Throw the typed errors in `src/errors.js` (`ConfigError`, `SectionError`,
  `GitError`, `GitHubApiError`) so failures include an actionable hint.
- Treat every value from an event payload as untrusted. Escape it with
  `escapeMarkdown`/`escapeInlineCode` before it reaches markdown or logs.
- Keep output deterministic: sort events by date and id, and avoid timestamps
  unless the user opts in.
- Add or update tests for every behavior change.
- Update the relevant file in `docs/` and `README.md` when inputs, outputs, or
  event support changes.
- Add a `CHANGELOG.md` entry under **Unreleased**.

## Tests

```bash
npm test
```

The suite uses `node:test` and covers unit, integration, and end-to-end paths,
including a temporary git repository and bare remote. New event types need a
serializer test; new inputs need validation tests; git changes need a test that
exercises a real repository where possible.

## Pull requests

- Keep changes focused and scoped to a single concern.
- Describe the user-visible behavior and link related issues.
- Include tests and documentation.
- Make sure `npm run verify` passes and `dist/` is rebuilt.
- Be responsive to review feedback.

## Commit messages

Conventional Commits are appreciated but not required:

```text
feat: support PullRequestReviewEvent
fix: respect MAX_LINES when the section has fewer lines
docs: document GH_USERNAME lists
```
